How it works

The two mechanisms that make a relational database a genuinely safe queue.

FOR UPDATE SKIP LOCKED

Twenty workers poll the same table at once. This is what stops them from all claiming the same rows.

ApproachResult
SELECT then UPDATESame job runs 20 times
SELECT … FOR UPDATECorrect, but serialized — no throughput gain
SERIALIZABLECorrect, but workers burn CPU retrying conflicts
SKIP LOCKEDNo blocking, no duplicates, scales with workers
WITH claimed AS (
  SELECT id FROM jobs
   WHERE status='pending' AND available_at <= now()
   ORDER BY priority DESC, available_at ASC, id ASC
   FOR UPDATE SKIP LOCKED LIMIT $1
)
UPDATE jobs SET status='running', lease_epoch = lease_epoch + 1, …
  FROM claimed WHERE jobs.id = claimed.id
RETURNING …

Leases + fencing tokens

The failure a naive lease misses: a worker doesn't crash, it freezes (GC pause, VM suspend), then wakes up and tries to write a result for a job someone else now owns.

  1. t=0 worker-A claims job J, lease 30s
  2. t=5 worker-A freezes
  3. t=31 reaper reclaims J → pending
  4. t=32 worker-B claims J, epoch bumped to 2
  5. t=33 worker-A wakes, tries to complete J with epoch 1
UPDATE jobs SET status='completed', …
 WHERE id=$1 AND worker_id=$2
   AND lease_epoch=$3 AND status='running'
-- worker-A's epoch is stale → matches 0 rows
-- it learns it lost, discards its result

This doesn't stop the side effect happening twice (worker-A may have already sent an email) — which is why the guarantee is at-least-once, and handlers must be idempotent.

Why PostgreSQL, not Redis or Kafka

Two reasons that matter more than raw throughput.

One transaction, not two systems

A job's state change and the business row it produces can commit in the same Postgres transaction. With Redis as the queue, those are two separate systems and you must build reconciliation between them.

Durability by default

Redis's default persistence can lose the last fsync window. For a queue, that means silently losing accepted work — unacceptable for something like a payment confirmation.

Conceded: Redis is faster

The position taken is "PostgreSQL until measurements say otherwise" — and it's backed by the benchmark numbers below, not a guess.

When Redis/Kafka would actually get introduced: when claim latency stops being dominated by the network round trip and starts being dominated by lock contention on the index — or when the real need is fan-out to independent consumers, which is a log, not a queue.

Stack

Go 1.26

Goroutines + channels give a structural concurrency bound — a buffered channel as a semaphore, not a thread pool library.

PostgreSQL 16 + pgx/v5

No ORM. Raw SQL because the correctness lives in SKIP LOCKED, partial indexes and CHECK constraints.

net/http stdlib

Go 1.22's ServeMux got method + wildcard routing, so no router dependency was needed.

log/slog

Structured JSON logs; a custom LogValuer makes the DB password structurally unable to leak into logs.

Prometheus + Grafana

Custom business metrics like queue age, not just infra metrics.

Docker + Compose

Multi-stage distroless builds, 27.8MB images, horizontal worker scaling via --scale.

golang-migrate

Schema migrations run as a deliberate one-shot step, never automatically on API boot.

k6

Load testing with a constant-arrival-rate executor, not fixed VUs — so a slowing server doesn't hide overload behind less load.
